# HypnoOS 核心開發與改動流程規範

> **開發期提醒**：目前專案正處於基於 MockAPI 進行快速迭代的開發期。因此，本文件之流程重點規範在 MockAPI 架構下如何新增與修改功能。

---

## 1. 資料結構修改規則

### 1.1 預設不進行 Fallback
* **核心規範**：在修改資料結構、重構或擴充功能時，**預設「不進行 fallback」直接使用新資料**。
* **目的**：為了在開發迭代中快速暴露數據不一致或缺失的 bug，檢驗重構是否成功。
* **疑慮確認**：如在是否需要相容舊資料存有疑慮時，需向用戶明確詢問。

---

## 2. 新增"桌面應用" (Desktop App) 流程

當需要在系統中新增桌面應用程式時，請遵循以下步驟：

1. **`AppMode` 註冊**：在前端的 `types.ts` 列舉中添加新 App 的 mode 識別碼。
2. **Mock 狀態註冊**：在 MockAPI 或對應數據庫中，為新 App 註冊初始狀態（如：是否預設解鎖、解鎖所需條件等）。
3. **主入口整合**：在 `App.tsx` 的 App 渲染清單中，添加該 App 的點擊 case 與圖示入口。
4. **數據隔離存取**：組件透過調用 MockAPI 來存取該 App 的狀態，嚴禁直接在 UI 組件中做解鎖條件的邏輯判定。

---

## 3. 新增消息構造協議 (Message Pipeline)

當需要與 AI 對話，使用 Pipeline 傳輸數據時，遵守以下步驟：

1. **準備階段**：在專屬 App 的 constants 檔案或 MockAPI 中定義該協議所需的 Prompt 模組、變數佔位符。
2. **構造參數**：於前端調用時，將情境參數轉化為 Pipeline 能接受的 `AiRequestParams` 格式。
3. **發送 (Mock/真實 Pipeline)**：統一調用 `AiRequestPipelineService` 接口進行發送與接收，**嚴禁在 UI 組件中手動拼接對話字串**。
4. **擺盤階段**：在收到 Pipeline 回傳結果後，由 MockAPI/Backend 進行 raw 值解析（如 JSON、YAML），並將更新後的狀態回寫至 Mock 數據庫。

---

## 4. 大型字串搬遷指引

若在重構時需要遷移大量的提示詞字串或數據：
* **做法**：在代碼中以註釋標記需要搬遷的區域與需求。
* **目的**：在任務的其餘部分都測試完成後，再讓用戶後續手動搬遷，避免單次修改量過大造成的 Token 過度消耗與 Git 衝突。

---

## 5. 專屬 APP 模組修改流程 (MockAPI 導向)

### 5.1 催眠 APP 功能 (Feature) 修改
1. **修改 Mock 列表**：在 MockAPI 對應的 feature 定義檔中，新增或修改該催眠功能（設定 `id`, `title`, `tier`, `costType` 等）。
2. **更新 Mock 運行時**：於 Mock 數據庫中為該 feature 實作購買與啟用狀態邏輯。
3. **UI 渲染與交互**：UI 組件透過 MockAPI 獲取該 feature 並自動分組渲染，點擊時透過 MockAPI 變更購買狀態。

### 5.2 角色編輯器 AI 流程修改
1. **更新欄位結構**：若新增或移除了角色屬性，同步修改 MockAPI 中的角色屬性結構。
2. **Mock AI 修改建議**：於 MockAPI 中實作模擬 AI 產生「修改建議 (Diff Proposals)」的邏輯。
3. **套用建議**：UI 組件呼叫 MockAPI 的套用接口，更新 Mock 記憶體數據庫。

### 5.3 成就與任務 (Quest) 功能修改
1. **擴充任務庫**：在 MockAPI 的成就/任務數據庫（如 `questDb`）中添加新任務/成就的名稱、描述與獎勵。
2. **判定點埋設**：在 MockAPI 的其他業務邏輯（如扣款、每日結算）中埋設判定點。
3. **觸發通知**：當滿足條件時，更新該成就為已解鎖狀態，並由 MockAPI 傳回通知，觸發 UI 彈出 Toast 提示。
