# HypnoOS 核心開發與改動流程規範

> **開發期提醒**：目前專案正處於基於 MockAPI 進行快速迭代的開發期。所有功能的改動均需圍繞 `models/`、`staticData/` 與 `database/` 的最新架構進行。

---

## 1. 資料結構修改規則

### 1.1 預設不進行 Fallback
* **核心規範**：在進行任何資料結構修改、重構或擴充功能時，**預設「不進行 fallback（不相容舊資料），直接使用新資料」**。
* **目的**：為了在開發迭代中快速暴露數據不一致或缺失的 bug，檢驗重構是否成功。
* **疑慮確認**：如在是否需要相容舊資料存有明確疑慮時，需向用戶提問。

---

## 2. 數據與合約優先的 6 步 APP 開發流程

當在系統中新增或大幅修改桌面應用（APP）或功能模組時，必須遵循以下「模型與合約優先 (Model & Contract First)」流程：

```
1. 需求與定位 ➔ 2. 資料模型與狀態設計 ➔ 3. MockAPI 接口合約 ➔ 4. UI 佈局考察 ➔ 5. 數據串接 ➔ 6. 極限測試
   (Scope)          (Model & State)        (API Contract)       (UI & Layout)       (Wiring)         (Validation)
```

### 2.1 第一步：需求與定位 (Scope)
* 釐清 APP 的核心玩法、催眠主題與使用者故事。
* 評估 APP 是否涉及運行時狀態變更（MC 能量、好感度、背包物品）或與 AI 對話（Pipeline 模式）。
* 檢查是否有可複用的通用機制，避免重複造輪子。

### 2.2 第二步：資料模型與狀態設計 (Model & State)
* **先於 UI 設計**。在 `models/index.ts` 中定義 APP 專屬的型別與數據結構，並在 `AppMode` 中添加新 App 的 mode 識別碼。
* 區分靜態常數（放入 `staticData/index.ts` 的靜態字典中）與運行時狀態變數（放入 `database/mvuVariables.ts` 或 `chatVariables.ts` 中）。
* 在 `database/mockDatabase.ts` 中新增該 APP 狀態的初始 Mock 數據。

### 2.3 第三步：接口與 API 設計 (API Contract)
* 在 MockAPI 中實作該 APP 的 Endpoint 與動作處理邏輯（如購買、接取、更新）。
* 定義明確的 UI 與邏輯的通訊合約。遵守**預設不 fallback** 規則。

### 2.4 第四步：UI 佈局與適配 (UI & Layout)
* 依據模擬手機 `9/19.5` 比例，在 `ui/` 下建立對應的 APP 組件資料夾與組件。
* 使用 Tailwind 標準原子類，依靠 `cqw` / `clamp` 全局流暢縮放與 Iframe 限制（禁用 vh/vw，使用百分比控制與 `overflow-y-auto`）。

### 2.5 第五步：數據串接與交互 (Wiring)
* 讓 UI 組件調用 MockAPI 接口來獲取與修改數據。
* 處理生命週期：在 `$(() => {})` 中執行初始化，在 `pagehide` 事件中卸載事件監聽。

### 2.6 第六步：極限測試與驗證 (Validation)
* 在倉庫根目錄執行 `pnpm build:dev` 確認編譯成功且無型別錯誤。
* 拉動瀏覽器視窗至極限尺寸（高度 <500px, 寬度 <320px）驗證響應式排版。
* 測試防呆邊界情況（如 MC 不足、背包滿）。

---

## 3. 新增消息構造協議 (Message Pipeline)

當需要與 AI 對話，使用 Pipeline 傳輸數據時，遵守以下步驟：

1. **準備階段**：在 `staticData/index.ts` 或 MockAPI 中定義該協議所需的 Prompt 模組、變數佔位符。
2. **構造參數**：於前端調用時，將情境參數轉化為 Pipeline 能接受的 `AiRequestParams` 格式。
3. **發送與接收**：統一調用 `AiRequestPipelineService` 接口進行發送與接收，**嚴禁在 UI 組件中手動拼接對話字串**。
4. **擺盤階段**：在收到 Pipeline 回傳結果後，由 MockAPI 進行 raw 值解析（如 JSON、YAML），並將更新後的狀態回寫至 Mock 數據庫。

---

## 4. 大型字串搬遷指引

若在重構時需要遷移大量的提示詞字串或數據：
* **做法**：在代碼中以註釋標記需要搬遷的區域與需求。
* **目的**：在任務的其餘部分都測試完成後，再讓用戶後續手動搬遷，避免單次修改量過大造成的 Token 過度消耗與 Git 衝突。
