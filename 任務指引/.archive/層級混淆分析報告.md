這是一份關於 HypnoOS 專案層級職責混淆嚴重度的詳細審查報告（第一部分）。由於代碼量較大，我將分次進行彙報。

### 🚨 總體嚴重度評估：高

專案雖然經歷過重構（引入了 `managers/`），但多個核心檔案仍然存在嚴重的「**上帝物件 (God Object)**」、「**依賴倒置 (Reverse Dependency)**」與「**職責越界**」問題。

---

### 1️⃣ `dataService.ts` 與 `managers/` 的依賴倒置與 Facade 破壞

**嚴重度：極高**
**問題描述**：`dataService.ts` 理應只是一個對外的 Facade，負責轉發呼叫給具體的 Managers。但實際上，它卻將最底層的 Core 邏輯（如 `getUserDataCore`、`updateResourcesCore`）直接暴露，甚至讓 Managers 依賴這些由外部傳入的 Core 函數，導致循環依賴與邊界模糊。

**代碼分段審查**：

在 `src/催眠APP前端/services/managers/systemCoreManager.ts` 中：
```typescript
// 這裡定義了核心的變數讀寫邏輯，這是正確的下沉
export async function getUserDataCore(): Promise<UserResources> { ... }
export async function updateResourcesCore(newData: Partial<UserResources>): Promise<UserResources> { ... }
```

但在 `src/催眠APP前端/services/managers/resourceManager.ts` 中，它卻直接依賴了 `systemCoreManager`：
```typescript
import {
  readStoreSnapshot,
  updateStoreWith,
  getUserDataCore,
  updateResourcesCore,
} from './systemCoreManager';

export function createResourceManager() {
  async function subscribeOrRenewImpl(...) {
    // ...
    const user = await getUserDataCore(); // ❌ Manager 應該透過 Repository 或 DI 獲取資料，而不是直接依賴另一個 Manager 的 Core 函數
    // ...
    await updateResourcesCore({ money: user.money - price });
  }
}
```
同時，`dataService.ts` 仍然保留了對這些 Core 的直接呼叫：
```typescript
  getUserData: async (): Promise<UserResources> => {
    return await getUserDataCore(); // ❌ Facade 應該呼叫 ResourceManager.getUserData()，而不是直接呼叫 Core
  },
```
**結論**：`systemCoreManager` 變成了一個隱形的「全局函數庫」，破壞了 `resourceManager` 應有的封裝。`dataService` 和 `resourceManager` 都在呼叫 `systemCoreManager`，導致資料流向混亂。

### 2️⃣ `characterDataService.ts` 的上帝物件化 (God Object)

**嚴重度：極高**
**問題描述**：這個檔案超過 300 行，承載了至少四種完全不同的職責：世界書 API 操作、YAML 與 AST 的雙向轉換、業務邏輯驗證、以及 EJS 模板的字串拼接。違反了單一職責原則 (SRP)。

**代碼分段審查**：

**職責 A：世界書 API 呼叫（應屬於 Repository 層）**
```typescript
// ❌ 業務邏輯層直接呼叫底層 Repository，且混雜在解析邏輯中
const wbName = WorldBookRepository.getCurrentCharacterWorldbook();
const entries = await WorldBookRepository.getEntries(wbName);
```

**職責 B：正則表達式與字串解析（應屬於 Parser/Helper 層）**
```typescript
// ❌ 寫死在 Service 中的硬編碼正則表達式
function buildXmlBlockRegex(charName: string) {
  return {
    dataRe: new RegExp(`<${escaped}(?:人设|人設)>[\\s\\S]*?\`\`\`yaml\\n([\\s\\S]*?)\`\`\`[\\s\\S]*?<\\/${escaped}(?:人设|人设)>`, 'm'),
    // ...
  };
}
```

**職責 C：YAML ↔ AST 轉換（應屬於 Mapper 層）**
```typescript
// ❌ 直接在載入邏輯中處理 YAML 解析
const parsed = YAML.parse(dataMatch[1]);
const nodes = yamlToTree({ [yamlKey]: value }, locked);
sectionData[sectionId] = [...(sectionData[sectionId] ?? []), ...nodes];
```

**職責 D：模板渲染與字串拼接（應屬於 Template/View 層）**
```typescript
// ❌ 在 saveCharacter 中手動拼接巨大的字串
behaviorParts.push(`### 当前状态`);
behaviorParts.push(`Variables:`);
behaviorParts.push(`  性欲: {{get_message_variable::stat_data.角色.${charName}.发情值}}`);
```

**結論**：`characterDataService.ts` 是一個典型的義大利麵條代碼 (Spaghetti Code)，任何對解析規則、世界書結構或模板內容的修改，都需要進入這個巨大的檔案中尋找。

### 3️⃣ `worldBookService.ts` 與 `characterDataService.ts` 的職責重疊

**嚴重度：中高**
**問題描述**：兩個檔案都在處理與世界書 `[mvu_plot]` 相關的邏輯，缺乏統一的上下文管理。

**代碼分段審查**：
在 `worldBookService.ts` 中：
```typescript
// 負責建立 [mvu_plot] 條目
function buildPlotRoleProfileEntryName(roleName: string): string {
  return `${PLOT_PREFIX}${roleName}人设`;
}
```
在 `characterDataService.ts` 中：
```typescript
// 負責讀取和更新 [mvu_plot] 條目
const PLOT_ENTRY_RE = /^\[mvu_plot\](.+?)(?:人设|人設)$/;
```
**結論**：關於 `[mvu_plot]` 的命名規則、前綴定義被分散在兩個不同的 Service 中。如果未來要修改世界書條目的命名規則，必須同時修改這兩個檔案，極易產生 Bug。
