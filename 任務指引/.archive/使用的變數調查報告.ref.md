# HypnoOS 變數系統架構與效能分析報告

## 1. Context (背景與目的)
使用者詢問了關於 HypnoOS 變數系統（聊天變數、MVU 變數、iframe 變數）的核心疑問：
1. 為什麼後端同時使用 Chat 變數與 MVU 變數？能否簡化為單一系統？
2. 在 500+ 層以上的深度對話中，將所有資料儲存於 MVU 是否會造成系統延遲 (Lag)？
3. (追加提問) 為什麼有些 MVU 變量能設置成不能被 AI 編輯？這是怎麼做到的？
4. (追加提問) 有沒有更簡單的方法或架構，可以處理大量資料又能支援 CRUD？

本報告旨在透過分析現有架構，解答這些疑問，並說明系統為確保高效能所採取的架構策略。

## 2. 核心分析與報告內容

### 2.1 為什麼後端同時使用 Chat 變數與 MVU 變數？能否簡化為單一系統？

在 HypnoOS 中，Chat 變數與 MVU 變數扮演著截然不同且不可互相替代的角色，因此**無法簡化為單一變數系統**。

1. **Chat 變數 (`系统._hypnoos`) —— 全局的「單一真相來源」(Source of Truth)**
   - **作用**：跨越整個聊天週期的持久化儲存。
   - **應用場景**：儲存使用者的全局設定、解鎖的成就，以及行事曆 (Calendar) 等佔用較大空間的「重型資料」。這些資料不受特定對話節點影響，是整個系統的基石。
2. **MVU 變數 (Message Variables) —— 維持「上下文一致性」(Contextual Consistency)**
   - **作用**：與特定的訊息 ID (Message IDs) 及滑動切換 (Swipes) 深度綁定。
   - **應用場景**：當使用者在聊天紀錄中「往回捲動」或「滑動切換不同的 AI 回覆分支」時，MVU 變數能確保 AI 讀取到的狀態與該時間點完全一致（即時間旅行能力）。若僅使用 Chat 變數，使用者回溯對話時會發生狀態錯亂。
3. **Iframe 變數 —— 暫時性運行狀態**
   - 僅作為執行期間的暫時性變數，不涉及持久化狀態的保存（重新整理即消失）。

**結論**：若僅使用 Chat 變數，系統將失去「時間旅行」與「分支切換」的能力；若僅使用 MVU 變數，則會導致不必要的重型資料隨對話分支無限膨脹。兩者相輔相成，不可或缺。

### 2.2 在 500+ 層級下，MVU 是否會導致延遲 (Lag)？

使用者常擔心深度對話會導致 MVU 變數過於龐大進而引發延遲，但 HypnoOS 後端已針對此問題實作了完善的**延遲緩解 (Lag Mitigation) 機制**，因此**不會造成延遲**。

1. **分層繼承架構 (Layered Inheritance)**
   - MVU 變數並不會在每一層 (Layer) 都複製一整份完整的資料。它採用了類似原型鏈的「繼承」設計，只有在該層發生「變更」的資料才會被記錄下來。這大幅降低了記憶體消耗與讀取壓力。
2. **重型資料的差異化節點與快照機制 (Diff/Node-based Architecture & Snapshots)**
   - 針對如「行事曆」這類重型資料，系統將其與對話層數 (Floor) 或滑動 ID (SwipeId) 綁定，採用差異化 (Diff) 儲存架構。
   - **快照機制**：系統每隔 50 層 (Floors) 就會自動建立一次狀態快照 (Snapshot)。當需要讀取特定層數的資料時，系統只需載入最近的快照，並計算剩餘層數的差異 (Diffs) 即可，完全避免了從第 1 層運算至第 500+ 層的龐大效能開銷。

### 2.3 為什麼有些 MVU 變量能設置成不能被 AI 編輯？這是怎麼做到的？

這是透過**提示詞控制 (Prompt Engineering)** 與 **後端攔截 (Backend Interception)** 雙管齊下達成的：

1. **命名約定與世界書隱藏**：
   根據專案規則（見 `MVU角色卡說明.md`），所有以 `_` 開頭的變數（例如 `_MC能量`）都被定義為唯讀。在撰寫世界書的 `[mvu_update]變量更新規則` 時，開發者會**刻意省略**這些帶有 `_` 前綴的變數。因為 AI 沒有收到更新這些變數的規則與指令，自然就不會在回覆中嘗試修改它們。
2. **底層事件攔截 (防呆機制)**：
   即使 AI 產生了幻覺嘗試修改唯讀變數，後端可以透過監聽 `Mvu.events.VARIABLE_UPDATE_ENDED` 或 `COMMAND_PARSED` 事件。在這些事件中，後端會檢查即將更新的變數列表，如果發現有對 `_` 開頭變數的修改，就會將其強制還原或拋棄，從而確保唯讀變數的絕對安全。

### 2.4 處理大量資料且支援 CRUD 的架構建議 (簡化方案)

目前的日曆 (Calendar) 採用了複雜的「快照+差異化節點」架構，這是為了同時滿足「大量資料 CRUD」與「支援時間旅行 (回溯樓層)」的嚴苛要求。如果您希望有更簡單的替代方案，可以考慮以下幾種架構：

*   **方案 A：放棄時間旅行，純全局 CRUD (最簡單)**
    *   **做法**：將資料純粹儲存在 Chat 變數 (`系统._hypnoos`) 中，**不綁定任何樓層資訊**。新增、刪除、修改就如同一般資料庫操作。
    *   **優點**：架構極度簡單，開發快速，無須處理複雜的快照邏輯。
    *   **缺點**：若玩家滑動回舊樓層，這些資料不會跟著回退（例如回到第 10 層，日曆上還是顯示第 100 層新增的行程）。
    *   **適用場景**：不影響劇情回溯的全域資料（如全域圖鑑、解鎖畫廊、玩家總成就）。
*   **方案 B：泛型化的時間旅行狀態庫 (Generic Time-Travel Store)**
    *   **做法**：將日曆現有的「快照+差異」邏輯抽離，封裝成一個通用的 Class (例如 `TimeTravelCrudStore<T>`)。
    *   **優點**：未來任何需要大量資料 CRUD 又要支援時間旅行的功能，只需實例化這個類別即可，開發者不需要再重新刻寫複雜的快照邏輯，降低了使用門檻。
*   **方案 C：IndexedDB 外部儲存 (針對極巨量資料)**
    *   **做法**：若資料極度龐大（如圖片、超長文本的筆記），連 Chat 變數都塞不下，可將實際資料存入瀏覽器的 `IndexedDB`（透過 Dexie.js 等套件），並在 MVU 或 Chat 變數中只記錄資料的 `ID` 或 `Hash`。
    *   **優點**：完美解決容量限制，且能透過 ID 輕鬆進行 CRUD。
