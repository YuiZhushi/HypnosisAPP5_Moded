## 🔍 發現的問題

### 1️⃣ 過度分層問題 ⚠️ **嚴重**

**問題描述**：調用鏈過長，存在 4-5 層轉發

```
組件 → DataService → DomainService → UsecaseService → Helper → Store
```

**具體例子**（以 `claimAchievement` 為例）：
```
AchievementApp.tsx
  → DataService.claimAchievement()
    → achievementQuestDomainService.claimAchievement()
      → hypnoAppUsecaseService.claimAchievement()
        → 多個 deps 函數
```

**問題**：
- `DomainService` 層幾乎只是簡單轉發，沒有實際業務邏輯
- `calendarService.ts`、`featureService.ts`、`subscriptionService.ts` 等都是 50 行左右的純轉發層
- 每增加一個功能都要穿透 3-4 層

---

### 2️⃣ 名稱混淆問題 ⚠️ **中等**

**問題列表**：

| 文件名 | 問題 |
|--------|------|
| `featureConstants.ts` | 只有 11 行，定義一個空的 Set，與 `features.ts` 功能高度相關但分離 |
| `calendarCrudResolver.ts` vs `calendarCrudStore.ts` vs `calendarEventImpl.ts` | 三個文件職責重疊，命名難以區分 |
| `achievementQuestCore.ts` vs `achievementQuestImpl.ts` | Core 和 Impl 的區分不明確 |
| `customHypnosisService.ts` (domain) vs `customHypnosisCost.ts` (helper) | 相關邏輯分散 |

---

### 3️⃣ 邏輯分散問題 ⚠️ **中等**

**日曆相關邏輯分散在 4 個文件**：
- `calendarService.ts` (domain) - 純轉發
- `calendarEventImpl.ts` (helper) - 實際實現
- `calendarCrudResolver.ts` (helper) - 解析邏輯
- `calendarCrudStore.ts` (helper) - Store 操作

**成就/任務邏輯分散在 3 個文件**：
- `achievementQuestService.ts` (domain) - 純轉發
- `achievementQuestImpl.ts` (helper) - 實際實現
- `achievementQuestCore.ts` (helper) - 核心邏輯

---

### 4️⃣ dataService.ts 臃腫問題 ⚠️ **嚴重**

**問題**：
- 844 行代碼
- 大量依賴注入代碼（100+ 行的 import）
- 300+ 行的服務實例化代碼
- Facade 模式變成了「大雜燴」

**依賴注入示例**（過於複雜）：
```typescript
const hypnoAppUsecaseService = createHypnoAppUsecaseService<
  PersistedStore,
  CustomHypnosisDef,
  Achievement,
  QuestDefinition,
  UserResources
>({ /* 43 個依賴項... */ });
```

---

### 5️⃣ 過度封裝問題 ⚠️ **中等**

**Domain Service 的「空殼」問題**：

```typescript
// calendarService.ts - 純轉發，沒有任何業務邏輯
export function createCalendarService<TEvent>(deps: CalendarServiceDeps<TEvent>) {
  return {
    getCalendarEvents(): TEvent[] {
      return deps.getCalendarEventsImpl();  // 直接轉發
    },
    // ... 其他方法也都是直接轉發
  };
}
```

這種封裝沒有價值，反而增加了調用鏈深度。

---

### 6️⃣ Helper 層職責不清 ⚠️ **輕微**

**問題**：
- `calendarCrudResolver.ts` 和 `calendarCrudStore.ts` 職責重疊
- `achievementQuestCore.ts` 和 `achievementQuestImpl.ts` 的邊界模糊
- 部分 helper 應該是 domain 邏輯

---

## ✅ 做得好的地方

1. **類型安全**：使用 TypeScript 和 Zod 確保類型安全
2. **依賴注入**：工廠函數模式便於測試
3. **Store 抽象**：`storeGateway.ts` 設計良好
4. **組件層乾淨**：組件只調用 DataService，沒有直接操作底層
