# HypnoOS 專案架構分析報告 (2026-04 最新版)

---

## 📊 專案結構總覽 (當前狀態)

經過早前的重構，專案的基礎服務層 (`services/`) 已經建立了 `managers/` 目錄並將許多業務邏輯聚合。但在深入檢查後，發現仍有許多深層的架構問題：

```
src/催眠APP前端/
├── components/          
├── services/            
│   ├── dataService.ts   # Facade 入口 (558行) - 仍包含核心邏輯與臃腫的 DI
│   ├── mvuBridge.ts     
│   ├── access.ts        
│   ├── worldBookService.ts # 世界書操作 (400+行)
│   ├── characterDataService.ts # 角色/世界書資料解析 (1100+行) [God Object]
│   ├── characterCompletionApp*Service.ts # 命名過長的服務群
│   ├── aiRequestPipelineService.ts 
│   ├── managers/        # 業務邏輯聚合層 
│   ├── store/           
│   └── helpers/         
```

---

## 🔍 核心架構問題分析

### 1️⃣ 邏輯跨層調用與依賴倒置 (Reverse Dependency)
**問題位置**：`dataService.ts` 與 `managers/`
- **現狀**：`dataService.ts` 作為對外的 Facade 層，卻在內部實作了最核心的 `getUserDataCore`、`updateResourcesCore`、`getSystemClockCore` 與 `syncSubscriptionTierLabel` 等邏輯。
- **過度封裝**：Facade 將這些核心函式透過參數（Dependency Injection）向下注入給 `resourceManager`、`featureManager`、`customHypnosisManager`、`achievementQuestManager`。
- **影響**：這導致了嚴重的依賴倒置，Facade 層變得臃腫（558 行），Managers 的初始化代碼充滿 Boilerplate，且層級邊界被破壞。

### 2️⃣ 層級臃腫：God Object 的誕生
**問題位置**：`characterDataService.ts` (1100+ 行)
- **現狀**：該檔案承擔了過多不相關的職責，違反單一職責原則 (SRP)。
  1. YAML ↔ AST (EditorNode) 的雙向解析。
  2. 呼叫 iframe 全域 API 讀寫 Worldbook。
  3. EJS 行為指導分支的 Regex 解析、驗證與排序。
  4. 角色預設模板 (Default Templates) 的生成。
- **影響**：檔案過於龐大，難以維護，且包含了底層資料解析與高層業務邏輯的混合。

### 3️⃣ 邏輯分散與重複實作
**問題位置**：`worldBookService.ts` 與 `characterDataService.ts`
- **現狀**：兩者都在呼叫全域 API（`getWorldbook`、`updateWorldbookWith`、`getCharWorldbookNames`）來操作世界書。
- **現狀**：兩者都在處理與 `[mvu_plot]` 相關的邏輯（`worldBookService` 負責人物列表與初始化，`characterDataService` 負責讀寫角色資料）。
- **影響**：缺乏統一的 Repository 層來處理世界書 API 的 I/O，導致相同的查詢與防錯邏輯散落在不同檔案中。

### 4️⃣ 名稱混淆與指向性問題
**問題位置**：`characterCompletionAppAiPatchService.ts`、`characterCompletionAppDiffService.ts`、`characterCompletionAppMergeService.ts`
- **現狀**：服務名稱極度冗長，且帶有重複的 `characterCompletionApp` 前綴。
- **影響**：降低代碼可讀性，且這種命名方式通常暗示了過度碎片化的模組拆分，這些服務本質上只是 AST 處理的 Utils 或 Helpers。

---

## 🎯 結論
雖然之前已經清理了 Usecases，但目前的系統在**「角色與世界書編輯器」**以及**「全域資源狀態管理」**上仍存在嚴重的設計缺陷。

需要進行新一輪的重構，重點在於：
1. **建立獨立的 Worldbook Repository**，收斂 API 呼叫。
2. **拆解 characterDataService.ts**，分離資料結構轉換與業務邏輯。
3. **消除 dataService.ts 的依賴倒置**，將資源核心邏輯下放至對應 Manager 或 Store。
4. **清理命名空間**，讓冗長的服務名稱回歸合理。
