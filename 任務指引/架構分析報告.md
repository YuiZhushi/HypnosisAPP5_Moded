## 📊 專案結構總覽 (當前狀態)

經過近期的重構，專案的服務層 (`services/`) 已經有顯著的改善。當前結構如下：

```
src/催眠APP前端/
├── components/          # React 組件層
├── services/            # 服務層（核心）
│   ├── dataService.ts   # Facade 入口（約 609 行）
│   ├── mvuBridge.ts     # MVU 橋接
│   ├── access.ts        # 權限控制
│   ├── constants/       # 常數定義 (如 features.ts, subscriptionConstants.ts 等)
│   ├── helpers/         # 純函數工具與具體實作邏輯 (如 systemHelpers.ts 等)
│   ├── managers/        # 業務邏輯聚合層 (新增：整合了日曆、資源、設定、成就任務、功能等)
│   ├── store/           # Store 與狀態遷移管理
│   ├── types/           # 內部持久化與狀態類型定義
│   └── usecases/        # 用例服務 (hypnoAppUsecaseService.ts)
├── prompts/             # 消息構造
├── data/                # 靜態數據
└── types.ts             # 全局類型定義
```

## 🔍 問題追蹤與狀態分析

### 1️⃣ 過度分層問題 ✅ **已解決**
**原問題**：調用鏈過長，存在 4-5 層轉發（組件 → DataService → DomainService → UsecaseService → Helper → Store）。
**當前狀態**：`DomainService` 層已完全移除。現在的架構是 `組件 → DataService → Managers / Usecases`，調用路徑清晰直接。

### 2️⃣ 邏輯分散與名稱混淆問題 🔄 **大幅改善**
**原問題**：模塊邏輯分散在多個 Helper/Impl 檔案中，邊界模糊。
**當前狀態**：
- 已經成功建立了 `managers/` 目錄，並將日曆 (`calendarManager.ts`)、成就與任務 (`achievementQuestManager.ts`)、設定 (`settingsManager.ts`)、資源 (`resourceManager.ts`)、功能 (`featureManager.ts`) 等核心業務進行了聚合。
- **遺留問題**：「自訂催眠 (Custom Hypnosis)」相關的邏輯依然部分散落在 `hypnoAppUsecaseService.ts`、`helpers/customHypnosisCost.ts` 與 `dataService.ts` 中，缺乏專屬的 Manager。

### 3️⃣ 過度封裝與依賴注入臃腫問題 ⚠️ **中等 (主要待解決)**
**原問題**：Usecase 層過度封裝，依賴注入 (DI) 設計過於複雜。
**當前狀態**：
- `src/催眠APP前端/services/usecases/hypnoAppUsecaseService.ts` 中的 `HypnoAppUsecaseDeps` 介面異常龐大，包含大量只需直接 `import` 即可的純函數或常數（如 `makeId`、`calculateCustomHypnosisCost`、`getStorePurchases` 等）。
- 這種設計導致 `dataService.ts` 在實例化 `hypnoAppUsecaseService` 時需要撰寫大量樣板代碼 (Boilerplate)，增加了維護成本。

### 4️⃣ dataService.ts 檔案臃腫問題 🔄 **部分解決**
**原問題**：`dataService.ts` 有 800+ 行。
**當前狀態**：
- 目前已瘦身至 609 行。大量核心邏輯已移至 `managers/`。
- **遺留問題**：由於 `hypnoAppUsecaseService` 的臃腫初始化，以及部分直連邏輯（如 Custom Hypnosis），檔案仍有進一步瘦身的空間。

## 🎯 結論與下一步方向

目前的架構已經從「過度分層」的泥沼中脫身，走向了較為扁平的 `Facade -> Manager` 結構。
