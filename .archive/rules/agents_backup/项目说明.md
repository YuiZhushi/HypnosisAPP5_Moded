# HypnoOS 專案說明與核心架構規範

> 本說明適用於 `src/` 樹下的開發與修復工作，特別是 `src/催眠APP前端/` 及其相關模組。

## 1. 專案概覽與環境假設

HypnoOS 是一個基於酒館 (SillyTavern) 運行的模擬作業系統介面。專案採用**領域驅動分層架構 (Domain-Driven Layered Architecture)**，嚴格實施前後端分離，確保各個 APP 模組的獨立性、可維護性與資料流的清晰。

| 屬性 | 值 |
| ------ | ----- |
| 技術棧 | React + TailwindCSS（無 Vue） |
| 打包工具 | 倉庫根目錄 Webpack（**不使用** 本目錄的 Vite 配置） |
| 產物位置 | `dist/催眠APP前端/index.html` |
| 開發命令 | 倉庫根目錄 `pnpm watch` |
| 構建命令 | 倉庫根目錄 `pnpm build` 或 `pnpm build:dev` |

### 1.1 運行環境與全局變數

程式碼運行於酒館助手的 **iframe 環境** 中，以下全局對象**不需要 import，直接可用**：

*   `$`：jQuery，用於載入時機與事件綁定。
*   `getVariables` / `updateVariablesWith` / `replaceVariables`：酒館助手變數介面（**UI 層嚴禁直接調用**）。
*   `waitGlobalInitialized` / `eventOn`：事件與初始化工具。
*   `Mvu`：MVU 變數框架。
*   `createChatMessages` / `triggerSlash`：發送訊息與觸發命令。
*   `setChatMessages` / `getChatMessages`：讀寫聊天訊息。
*   `getCurrentMessageId` / `getIframeName`：獲取上下文資訊。

> ⚠ 純瀏覽器直接打開產物無法運行——這是預期行為。

### 1.2 專案頂層目錄劃分

*   **`src/催眠APP前端/`**：OS 的主體（包含 UI 介面與 Backend 邏輯）。
*   **`src/催眠APP監聽/`**：背景腳本，負責監聽酒館關鍵事件（如訊息刪除、滑動），並橋接至聊天變數供 iframe 讀取。
*   **`src/催眠APP脚本/`**：負責與 UI 無關的遊戲機制腳本（如每日結算、能量恢復）。
*   **`src/催眠APP共用/`**：各環境（前端、監聽、腳本）共用的基礎設施（如 `loggerService`）。
*   **`src/催眠APP變量結構/`**：MVU變量的結構，初次註冊變量結構使用。（包含結構定義）。

## 2. 前端目錄結構與職責劃分 (`src/催眠APP前端/`)

各 APP 的前後端文件必須**分開管理**，並嚴格遵守以下分層：

### 2.1 `ui/{APP_NAME}/` (前端 UI 層)

*   **職責**：負責 iframe 內的畫面渲染、使用者操作交互。
*   **規範**：OS 與各 APP 頁面風格需保持一致，版面配置合理。
*   **禁忌**：
    *   **絕對禁止**直接調用酒館助手的底層 API。
    *   **絕對禁止**直接操作 `localStorage`, `sessionStorage`, `indexedDB` 等本地存儲。
    *   所有資料存取與業務邏輯必須透過 `backend/{APP_NAME}/` 提供的 API。

### 2.2 `backend/{APP_NAME}/` (後端業務邏輯層)

*   **職責**：處理各 APP 專屬的業務邏輯、資料持久化與傳輸。
*   **規範**：如需訪問其他 APP 的功能，必須透過該 APP 後端提供的 API 進行，嚴禁跨 APP 直接操作 UI 狀態。

### 2.3 `shared/` (共用基礎設施層)

*   **職責**：存放多個 APP 重複使用的功能與底層橋接服務。如果可以分類於現有的 shared 目錄結構下最好，不行就建立新的類別資料夾。
*   **規範**：
    *   **資料讀寫與持久化**：必須透過 `shared/store/*` 或 `shared/mvu/mvuBridge.ts`。
    *   **世界書交互**：必須透過 `shared/worldbook/worldBookRepository.ts`，禁止直接調用酒館 API。
    *   **AI 請求管線**：必須交由 `shared/ai/aiRequestPipelineService.ts` 統一處理拼接與發送。
    *   **發送聊天訊息**：必須使用 `shared/llm/chatTransport.ts`。

### 2.4 `constants/{APP_NAME}/` (常數與資料層)

*   **職責**：集中管理各 APP 的大量常數、預置資料與 Zod Schemas。
*   **禁忌**：禁止在業務邏輯或 UI 檔案內自行宣告大量常設變數。

## 3. 核心實作規範與依賴限制

### 3.1 嚴格的單向依賴與防循環引用

*   **依賴方向**：`ui` -> `backend` -> `shared` -> `constants`。
*   **禁止事項**：嚴禁檔案間的循環引用、跨層級逆向引用（如 `shared` 依賴 `ui`），以及跨 APP 的直接內部引用。

### 3.2 變數生命週期與管理

開發時必須清楚區分以下三種變數的生命週期：

1. **Runtime 變數**：僅存在於 iframe 記憶體中，重新載入即消失，無法持久化。
2. **聊天變數 (Chat Variables)**：在單一對話內保持跨樓層通用，適合儲存全域狀態（如系統設定）。
3. **MVU 變數**：在不同樓層、不同 Swipe 中獨立儲存，並會自動繼承上一樓層的資料。適合儲存角色狀態、任務進度等與時間軸強相關的資料。

#### 3.2.1 資料與持久化契約參考

* **用戶資源（`UserResources`）→ 聊天變數 `系统`**：
  * `mcEnergy` -> `系统._MC能量`
  * `mcEnergyMax` -> `系统._MC能量上限`
  * `mcPoints` -> `系统.当前MC点`
  * `totalConsumedMc` -> `系统._累计消耗MC点`
  * `money` -> `系统.持有零花钱`
  * `suspicion` -> `系统.主角可疑度`
* **私有持久化 store（`系统._hypnoos` → `PersistedStore`）**：包含 `debugEnabled`, `sessionEndVirtualMinutes`, `sessionEndAtMs`, `subscription`, `features`, `achievements` / `quests` 等。
  * **寫入規則**：所有對 store 的寫入必須透過後端 API（如 `updateStoreWith(...)`）完成，寫入後自動調用 `MvuBridge.syncPersistedStore(...)` 做 MVU 同步。

### 3.3 事件監聽與橋接

*   許多酒館事件會發生在 iframe 載入前。因此，iframe 需要監聽的事件**必須**透過外部腳本 `@src/催眠APP監聽/index.ts` 註冊。
*   監聽到的事件狀態需寫入「聊天變數」，iframe 內部再透過讀取變數來感知事件發生。
*   **例外（UI 刷新觸發器）**：前端 UI 組件可以訂閱 `Mvu.events.*`（例如 `Mvu.events.VARIABLE_UPDATE_ENDED`）作為畫面刷新的觸發器，但**仍不可直接操作**底層變數。

### 3.4 AI 資料處理標準流程 (Pipeline)

當 APP 需要使用 AI 生成、編輯或解析資料時，必須遵循以下「食材與食譜」模式：

1. **準備 (APP 層)**：各 APP 負責準備專屬的提示詞模塊與模板（類似準備食材與食譜）。
2. **烹飪 (Shared 層)**：交由 `@src/催眠APP前端/shared/ai/aiRequestPipelineService.ts` 統一處理拼接、替換佔位符、發送請求與接收（類似做菜並遞回）。
3. **擺盤 (APP 層)**：各 APP 收到原始資料後，依照自己的格式需求進行解析與最終處理（類似調味與擺盤）。

## 4. UI 樣式與環境限制 (Iframe 特性)

由於程式碼運行於酒館 iframe 中，必須遵守以下限制：

### 4.1 載入與卸載事件

*   **禁止使用 `DOMContentLoaded`**：iframe 載入方式不會觸發此事件。請使用 jQuery 的 `$(() => { ... })`。
*   **禁止使用 `unload` 事件**：清理工作應使用 `pagehide` 事件。

### 4.2 樣式與排版 (TailwindCSS)

*   **優先使用 TailwindCSS 原子類**，避免散落的全局 CSS。
*   **禁止使用 `vh` / `vw` 單位**：會受宿主容器高度影響導致排版崩潰。請使用 `width` + `aspect-ratio` 或 Tailwind 的 `h-full w-full` 控制。
*   **避免撐高容器**：避免使用 `min-height`、`overflow: auto` 等會撐高外層容器的屬性。
*   **主體定位**：主體內容不要使用 `position: absolute`。
*   **禁止空 src**：禁止在 HTML 中使用 `src=""` 空佔位，會導致 Webpack 打包錯誤。

### 4.3 日誌規範

*   統一使用 `loggerService.ts` 進行輸出。
*   日誌統一前綴：`[HypnoOS]`。
*   關鍵節點用 `logger.info` 記錄；可恢復錯誤用 `logger.warn` / `logger.error`；致命錯誤用 `throw Error`。

## 6. 開發與驗證流程

### 6.1 開發前檢查清單

在開始修改前，必須確認：

* [ ] 理解了要改動的功能涉及哪些層級（UI, Backend, Shared, Constants）。
* [ ] 檢查相關的 Zod Schema 與型別定義。
* [ ] 檢查資料結構和變數映射是否正確。
* [ ] 如涉及 MVU 橋接，檢查 `mvuBridge.ts` 中的同步邏輯。

### 6.2 構建驗證

```bash
# 在倉庫根目錄執行
pnpm build:dev
```

* 確認**無編譯錯誤**。
* 確認產物 `dist/催眠APP前端/index.html` 正確生成。

### 6.3 類型與接口檢查

確保 TypeScript 無類型錯誤，特別關注各層級之間的型別是否保持一致，以及橋接介面調用是否正確。

### 6.4 運行時驗證（透過 chrome-devtools MCP）

如果已經連接了瀏覽器（酒館網頁），可以透過 chrome-devtools 進行運行時驗證：

1. **檢查熱重載是否可用**：確認酒館助手的"實時監聽"開關已啟用，代碼變更後介面應自動更新。
2. **檢查 Console**：確認沒有 `[HypnoOS]` 相關的錯誤日誌，關鍵流程有正確的 `logger.info` 輸出。
3. **UI 驗證**：截圖/快照確認介面渲染正確，驗證新增功能的交互是否正常。

### 6.5 變數驗證

改動涉及變數讀寫時，使用以下方式驗證：

* 透過 chrome-devtools `evaluate_script` 調用 `getVariables({type: 'chat'})` 檢查變數值。
* 確認寫入後的變數格式與 Zod Schema 定義一致。

## 7. 禁止事項

| 禁止 | 原因 |
| ------ | ------ |
| 手動修改 `dist/` 目錄 | 由打包流程自動生成 |
| 在本目錄執行 `npm run dev/build` | 已被禁用，必須用根目錄 Webpack |
| 使用 `DOMContentLoaded` | iframe 載入方式不會觸發此事件 |
| 使用 `vh` 單位 | 受宿主容器高度影響 |
| UI 組件直接寫變數 | 破壞單一資料源與前後端分離原則 |
| 在組件中拼消息字串 | 應交由 Backend/Pipeline 處理 |
| 使用 `'unload'` 事件 | 應使用 `'pagehide'` |
| 使用 `src=""` 空佔位 | 會導致 Webpack 打包錯誤 |
| 使用 Python/Node 腳本批量編輯 | 腳本不可用 |

```tsx
    const root = createRoot(container);

    $(window).on('pagehide', () => root.unmount());
  }
});
```

```ts
// mvuBridge.ts
```
